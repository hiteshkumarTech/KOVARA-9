# KOVARA-9 v0.1 ten-day sprint

## Research question and target

> Can parameter-sharing multi-agent reinforcement learning learn useful cooperative exploration
> strategies and generalize them to procedurally generated unseen environments?

The ten-day target is one reproducible experiment in which a shared policy learns cooperative
grid-rescue behavior and is evaluated against the existing random and frontier baselines on familiar
and held-out environment distributions. The implementation uses PyTorch and one MAPPO-style
clipped-policy learner. It does not attempt the long-term KOVARA-9 vision.

## Fixed scope

The actor is shared by homogeneous agents and receives only one agent's decentralized observation.
The critic is used only during training and receives the existing centralized `state()` view. The
learner has separate discrete movement and communication heads, honors both action masks, uses
Generalized Advantage Estimation (GAE), and optimizes a clipped PPO objective with value loss,
entropy regularization, and gradient clipping.

The v0.1 implementation is MAPPO-style rather than a claim of complete MAPPO reproduction. It uses
parameter sharing, centralized value estimation, decentralized execution, synchronous on-policy
rollouts, and PPO updates. Initial simplifications are feed-forward networks, homogeneous agents,
one shared team reward, no recurrent state, no population training, and no distributed rollout
service.

## Acceptance criteria

v0.1 requires all of the following:

1. A real PyTorch learner that completes an end-to-end update.
2. One actor shared by every homogeneous agent.
3. Actor inputs restricted to the documented local observation contract.
4. A centralized critic consuming only the separate centralized state adapter.
5. Clipped PPO policy optimization with independently masked move and message distributions.
6. Manually verified GAE and return calculations.
7. Checkpoint save, load, resume, and deterministic checkpoint evaluation.
8. Explicit simulator, rollout, minibatch, and model seed streams.
9. A bounded CPU smoke configuration; CUDA is optional and selected only when available.
10. Atomic training metrics, configuration, checkpoint, and provenance artifacts.
11. Comparisons against random, frontier, and untrained neural policies.
12. Evaluation on reference and structurally held-out configurations and held-out seeds.
13. Communication-enabled and communication-disabled evaluation; reduced budget is stretch scope.
14. At least three independent training seeds for final claims when the available compute budget
    permits them.
15. Mean, standard deviation, deterministic confidence intervals, and per-seed records.
16. Measured inference latency with the device and batch shape recorded.
17. Honest negative results, instability, and failure analysis.
18. A reproducible recruiter demo that completes in approximately five minutes.
19. A GitHub README that clearly separates implemented behavior, results, and future work.
20. No claim of emergent intelligence or production rescue readiness.

## Non-goals

The sprint excludes LLMs, external AI APIs, world models, imitation learning, 3D engines, WindArms,
microservices, databases, cloud infrastructure, Kubernetes, dashboards, additional learning
algorithms, and unsupported performance claims. Large checkpoints and raw training runs remain
ignored unless a later repository policy explicitly permits them.

## Technical boundaries

- `GridRescueParallelEnv` remains the sole owner of simulator transitions.
- Observation and state encoders adapt declared environment contracts into tensors; the networks do
  not import grid-rescue transition rules.
- Actor and critic have distinct forward methods and input types. Central state is never accepted by
  the actor API.
- The rollout collector owns multiple in-process environments. Vectorization is synchronous and
  intentionally local for v0.1.
- Torch, NumPy, environment, policy-sampling, and minibatch randomness use explicit derived seeds.
- The locked v0.1 Python target is 3.12 because the current
  [PyTorch installation guide](https://docs.pytorch.org/get-started/locally/) lists Windows support
  through Python 3.12.
- Numerical checks stop training on non-finite observations, logits, losses, or gradients.
- Checkpoint loading validates configuration and observation/action signatures before evaluation or
  resume.

## Experiment protocol

Training uses the configured reference environment and training seed partition. Model selection and
stability checks use validation seeds. Final records use held-out test seeds and never feed back into
optimization. Each final training seed produces an independent checkpoint and complete manifest.

The comparison matrix contains random, frontier, untrained shared actor, and trained shared actor on:

1. the reference environment with held-out seeds;
2. the structurally held-out environment with the same paired seeds;
3. communication enabled with the trained budget;
4. communication disabled;
5. a reduced communication budget if the required matrix finishes first.

Reported metrics are success rate, episode length, exploration coverage, duplicated exploration,
team efficiency, accepted communication cost, structural generalization gap, seed generalization
gap, and inference latency. Smoke output proves only pipeline correctness and is never presented as a
benchmark.

## Daily execution plan

### Day 1 — interfaces and foundations

- Safely publish the Phase 0.1 branch and preserve the original remote main history.
- Freeze this scope and the exact MAPPO-style simplifications.
- Add validated training configurations and portable path resolution.
- Add deterministic device/seed utilities, shared actor, centralized critic, tensor contracts, and
  rollout storage foundations.
- Unit-test network shapes, parameter sharing, information separation, configuration rejection, and
  rollout shapes.

Exit gate: all Phase 0 tests plus Day 1 tests pass on CPU; no rollout collection or optimizer is
claimed complete.

### Day 2 — rollout collection and masked actions

- Add synchronous multi-environment rollout collection.
- Enforce movement and communication masks in training and deterministic evaluation.
- Preserve terminal observations, episode boundaries, centralized critic state, and explicit seeds.
- Test invalid-action probability, stochastic sampling, deterministic selection, and boundary reset.

Exit gate: a bounded rollout can be collected without optimization and replayed for shape and seed
checks.

### Day 3 — GAE and PPO optimization

- Implement GAE, clipped policy loss, clipped or explicit value loss, entropy bonus, minibatches,
  gradient clipping, and learning-rate updates.
- Reject non-finite tensors, losses, and gradients with contextual errors.
- Test hand-calculated GAE/loss cases and confirm a controlled update changes parameters.

Exit gate: one numerically valid optimizer update passes focused tests.

### Day 4 — checkpoints, resume, evaluation, and CLI

- Add atomic checkpoint/model/optimizer/training-state persistence.
- Validate resume signatures and restore optimizer, counters, and RNG states.
- Add `train`, `evaluate-checkpoint`, and policy-comparison CLI workflows.
- Add deterministic checkpoint policy inference without centralized state.

Exit gate: save/load equality and interrupted-versus-resumed smoke training are verified.

### Day 5 — integration and CPU smoke

- Complete public-workflow tests and artifact provenance checks.
- Run the committed CPU smoke training configuration from a clean checkout.
- Audit decentralized actor and centralized critic data flow.

Exit gate: smoke training, evaluation, full test suite, package build, and CLI checks pass.

### Day 6 — stability and baseline comparison

- Diagnose learning curves, reward scaling, entropy collapse, invalid masking, and value divergence.
- Compare a trained smoke/small policy with random, frontier, and an untrained actor.
- Change configuration only with recorded rationale; do not tune on held-out test seeds.

Exit gate: the training pipeline is stable enough to schedule independent runs, or failure is
documented and the final experiment is reduced honestly.

### Day 7 — independent training seeds

- Run at least three `mappo_final` seeds if compute permits.
- Persist checkpoints and per-seed metrics outside Git.
- Evaluate reference performance on validation seeds before freezing model selection.

Exit gate: the final checkpoint set and exact manifests are immutable and enumerated.

### Day 8 — held-out and communication evaluation

- Evaluate frozen checkpoints on test seeds and the structural held-out environment.
- Run enabled/disabled communication ablations and the reduced-budget stretch run.
- Measure inference latency with warm-up and a documented timing method.

Exit gate: all compared records have matching seeds, fingerprints, and policy provenance.

### Day 9 — results and recruiter demo

- Produce tables and plots only from validated artifacts.
- Write results, limitations, and failure analysis without extrapolating beyond observed runs.
- Add the approximately five-minute recruiter demo scripts and README material.

Exit gate: every number in documentation can be traced to a committed protocol and an external run
artifact.

### Day 10 — release audit

- Verify a fresh locked installation, full quality suite, package build, smoke workflow, and CI.
- Review tracked files for secrets, caches, runs, and checkpoints.
- Confirm GitHub main contains the full project and improve repository metadata.
- Tag `v0.1.0` and create a release only if every definition-of-done condition passes.

Exit gate: otherwise leave the release untagged and publish the remaining blockers.

## Compute and claim gates

The smoke configuration is deliberately too small for a scientific conclusion. `mappo_small` is a
stability and integration run. Only `mappo_final`, repeated with at least three independent training
seeds and evaluated on untouched test seeds, is eligible for the results document. If time or compute
prevents that matrix, v0.1 reports an engineering MVP and the missing experiment as a limitation.

## Commit sequence

Day 1 uses separate reviewable commits for the sprint/configuration boundary and for network/rollout
foundations. Later commits follow the same pattern: rollout collection, optimization, checkpoints,
learner tests, evaluation, and documentation remain independently reviewable.

## Current release risks

- Remote main remains incomplete until the Phase 0.1 pull request is reviewed and merged.
- As documented in the
  [PyTorch reproducibility notes](https://docs.pytorch.org/docs/stable/notes/randomness), determinism
  is bounded to the recorded release, platform, device, and operation set; CPU and CUDA results are
  not assumed bitwise identical.
- A feed-forward actor may be insufficient for memory-dependent coordination; recurrence is deferred
  unless evidence from the single algorithm requires it.
- Final multi-seed training is compute-dependent and cannot be claimed before artifacts exist.
- Structural environments may require compatible local observation/action signatures for one actor;
  incompatible comparisons must fail validation rather than reshape silently.
