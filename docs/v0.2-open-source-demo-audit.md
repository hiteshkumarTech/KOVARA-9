# v0.2 open-source demo audit and implementation record

## Scope and baseline

This engineering audit started from commit
`877777d6a270fd6f79a3b707a573cc106d719b98` on the dedicated
`v0.2-open-source-demo` branch. The branch was clean and pointed at the same commit as the frozen
`v0.1.0` tag when the baseline checks began.

The objective is to make the smallest public demonstration portable, packaged, honest, and easy to
verify. This is not a new scientific experiment. The research question remains whether independently
executing agents can learn coordination from local observations and limited communication and retain
it on unseen procedural environments.

The following v0.1 evidence remains historical and immutable in this work:

- candidate and freeze definitions under `configs/training/`;
- the completed final-test consumption record;
- Day 5 through Day 10 experiment, preregistration, result, and audit records;
- committed result SVGs and their provenance manifest; and
- the recorded v0.1 learning claims and negative-result classification.

No training, final evaluation, checkpoint generation, result regeneration, tag operation, remote
write, or release publication is in scope.

## Findings and decisions

| Priority | Finding | Decision |
|---|---|---|
| High | The only guided end-to-end demonstration was PowerShell-first. | Add a native `kovara9 demo` command that is platform-neutral. Keep the longer PowerShell evidence tour intact. |
| High | The wheel contained code but no default runnable configuration, so a demo depended on repository paths. | Ship one strict YAML demo definition as a package resource and load it through the normal configuration boundary. |
| High | A public example could accidentally be mistaken for evaluation evidence. | Mark reports and logs as `behavioral_walkthrough_not_benchmark` and record explicit false flags for training, final evaluation, and learned-checkpoint loading. |
| High | Demo seed safety was enforced only in the PowerShell script. | Validate disjoint partitions and require every packaged demo seed to belong to the declared training range. |
| Medium | Rendering a new workflow could tempt simulator/UI coupling. | Expose only optional defensive snapshot observation from evaluation; renderers remain downstream and cannot issue transitions. |
| Medium | The short demo had no portable machine-readable handoff. | Write resolved YAML and deterministic JSON into a new, collision-safe output directory when requested. |
| Medium | Package discovery metadata omitted project links and keywords. | Add repository, documentation, issue, and research-domain metadata without changing dependencies. |
| Medium | CI did not exercise the shortest public entry point. | Add demo validation to CI and cover execution/artifacts through integration tests. |
| Low | Existing open-source policy files were concise but the immutable-evidence boundary was implicit in contribution guidance. | State that boundary and the local-observation/rendering rules in `CONTRIBUTING.md`. |

## Implemented workflow

The packaged demo definition declares the complete easy environment, the existing seed partitions,
two unique training-domain episode seeds, both existing baseline policy types, render selection, and
a bounded frame count. No research parameter is embedded invisibly in CLI control flow.

The `demo` command supports:

- default execution from the wheel;
- a user-supplied strictly validated YAML definition;
- `--validate-only` without creating an environment;
- `--render` or `--no-render` presentation modes; and
- `--output` for resolved YAML and a deterministic JSON report, refusing overwrite collisions.

Random and frontier policies still receive only each agent's local observation and personal outcome.
The evaluator calculates metrics from simulator facts and may send defensive snapshots to the ANSI
renderer. Rendering is excluded from the persisted report, so presentation selection cannot change
the recorded episode evidence.

## Verification plan

Before branch handoff, run all of the repository-required gates:

1. `uv lock --check` and `uv sync --locked` in a writable isolated environment.
2. `ruff format --check`, `ruff check`, and strict `mypy`.
3. The complete Pytest suite with a fresh temporary directory and the 90% coverage threshold.
4. Source and wheel builds, followed by inspection that the demo YAML is present in the wheel.
5. An installed-wheel `kovara9 demo --validate-only` smoke and a source-tree `demo --no-render`
   artifact smoke.
6. `git diff --check`, forbidden-artifact inspection, and a final diff review proving that frozen
   v0.1 result/configuration paths did not change.

Any failed gate remains a reported failure; none may be replaced by claimed evidence.
